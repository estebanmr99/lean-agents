## Windows

- `install.ps1` runs on PowerShell 5.1 and 7 and needs no admin rights.
- Tools come from winget (`rtk-ai.rtk`, `astral-sh.uv`). `real-winget` installs both without a TTY: rtk 1.1.0 and uv 0.13.6 on 2026-10-31.
- Without winget, extract `rtk-x86_64-pc-windows-msvc.zip` into `%USERPROFILE%\tools\rtk`; `install.ps1` adds it to the user PATH.
- No directory junctions are needed: the Skills CLI installs into `~/.claude/skills` and `~/.agents/skills`, and OpenCode reads `~/.agents/skills`.
- `rtk init` writes to the OS profile folder, not `USERPROFILE`. It only matters when testing with a temp `USERPROFILE`.
- OpenCode 2 on Windows: `opencode.ai/v2/install` runs through Git Bash, installs `opencode.exe` into `%USERPROFILE%\.opencode\bin` and only edits `~/.bashrc` / `~/.bash_profile` (`--no-modify-path` skips that), so PowerShell needs the user PATH entry added by hand. Verified on v2.2.5 (Authenticode valid). `npm i -g opencode-ai` installs 1.x, not 2.x. `install.ps1` finds that folder when `opencode` is not on PATH. Source: real install, #32, 2026-11-05. Real Windows PC (#179, 2026-11-19): the v2.2.5 installer replaces a 1.x `opencode.exe` in the same folder in place (and adds `opencode2.cmd`); a PATH entry left by the 1.x installer already covers it. So the 1.x binary must be copied aside first: `--upgrade-agent opencode --opencode1 --yes`, then the hand install, then the upgrade.
- Agent shell (#124, follow-up proven): the install summary and `--doctor` say whether Git Bash was found (`MSYSTEM` set, or `bash.exe` under `Program Files\Git\bin`); lean-agents now also sets OpenCode's `shell` key to that path by default on Windows (`--shell default` opts out; a `shell` you already set is kept). **Proven** on `windows-latest` with the real `real-opencode-shell` CI job (jobs 131467661473 for 1.19.0, 131467661406 for 2.2.5; date 2026-11-12), using a local mock OpenAI-compatible LLM (`tests/fixtures/mock-llm.mjs`) so the one bash/shell tool call needs no login: `shell` set to an absolute Git Bash path makes the tool run there (`$0`/`SHELL0` names `bash`) even with Git's own folders off PATH, for both 1.19.0 (tool name `bash`) and 2.2.5 (tool name `shell`). Without the key, or with `shell` set to `powershell.exe`, the probe's `MSYSTEM`/`$0` both come back empty on both majors — consistent with PR 16069's claim that Windows defaults away from Git Bash, though the probe cannot tell PowerShell and cmd.exe apart from that alone. The Git Bash case also ran through the real installer (`install.ps1 -NoCore -NoTools`), not a hand-written config, confirming the shipped adapter writes the same path. Precedence against `OPENCODE_GIT_BASH_PATH` and `opencode debug config` printing only sources on 2.2.6 stay **VERIFY**; neither blocks this default.
- The runner image has no winget; `real-winget` adds it with `Repair-WinGetPackageManager`.
- `install.ps1` bootstrap without git or winget (#179 PR4, 2026-11-18): git is not needed (the release is an npm tarball); without a clone of a previous install, nothing calls git. With no Node.js: `winget install OpenJS.NodeJS.LTS --scope user`, and if that fails or winget is absent, the nodejs.org zip (`latest-v24.x/SHASUMS256.txt` lists `node-vX.Y.Z-win-x64.zip` and `-win-arm64.zip` with SHA-256; a `.asc` and `.sig` exist but are not checked, so it is a corruption check from the same origin, not authenticity) extracted with .NET `ZipFile` (GNU tar on PATH cannot read zip) into `%USERPROFILE%\tools\node`, added to the user PATH. `-Uninstall` removes that folder and entry. Covered by `tests/windows-install.ps1` against a fake nodejs.org folder (`LEAN_AGENTS_NODE_DIST`); not yet seen green in CI. A host in `NO_PROXY` skips `HTTPS_PROXY` and uses the system proxy (no direct-connection switch in `Invoke-WebRequest`); the Windows login is offered to whatever proxy challenges. **VERIFY**: the zip layout (`node-vX.Y.Z-win-x64\node.exe` at its root) against a real zip; the manifest for `OpenJS.NodeJS.LTS` (26.13.1) declares only `Scope: machine` ([winget-pkgs#463823](https://github.com/microsoft/winget-pkgs/issues/463823)), so `--scope user` is expected to fail without admin and the zip then takes over.
- nvm-windows without admin (**VERIFY**, research 2026-11-18): nvm-windows v2.0.1 creates the `NVM_SYMLINK` directory link, and Windows restricts symlink creation ([nvm-windows#1326](https://github.com/coreybutler/nvm-windows/issues/1326), [Permissions wiki](https://github.com/coreybutler/nvm-windows/wiki/Permissions-Troubleshooting)): it needs an elevated shell or Windows Developer Mode, which is a policy choice. The README also mentions a symlink-free "shim mode" that could not be tied to `nvm use` from the docs. The CI runner is an administrator, so `real-tool-node.ps1` cannot prove the no-admin case; only a standard-user Windows account can. The bootstrap therefore does not depend on nvm-windows: it installs Node 24 directly. nvm-windows stays a planned step in `scripts/lib/prereqs.mjs` (run by the engine, PR2).
- Bootstrap downloads (2026-11-18): `[Net.ServicePointManager]::SecurityProtocol` gains Tls12 (5.1 defaults to 1.0/1.1). `Invoke-WebRequest` takes `-Proxy` from `HTTPS_PROXY` unless `NO_PROXY` lists the host (comma list, leading dot or `*` for subdomains; no CIDR), otherwise the Windows system proxy with the current login (`DefaultNetworkCredentials`, 5.1). A proxy URL with a password in it is not parsed. The values are read from the environment each time and never written to disk or printed. `NODE_EXTRA_CA_CERTS` reaches the engine through the environment, but PowerShell trusts only the Windows certificate store, so a TLS-inspecting proxy's CA must be installed there for the bootstrap's own downloads. Only the owner's PC can prove this behind a real proxy.
- The user PATH is now read and written as the unexpanded registry value (`REG_EXPAND_SZ`), so `%VARS%` in it survive. Registry edits do not notify other programs; the bootstrap sets and clears a dummy user variable to make Windows broadcast `WM_SETTINGCHANGE` ([`Environment.SetEnvironmentVariable`](https://learn.microsoft.com/en-us/dotnet/api/system.environment.setenvironmentvariable) documents the notification for User targets). Whether already-open terminals pick it up is unverified: open a new terminal. **VERIFY**
- macOS jobs cancelled with "job was not acquired by Runner" (#166, run 43249931041, 2026-11-12) are runner capacity, not a code failure; rerun them, do not change the workflow (**VERIFY** GitHub's runner-capacity wording).

## Staying on OpenCode 1.x

lean-agents never installs or upgrades OpenCode: the engine only writes config for the OpenCode you already have, and `--doctor` says "OpenCode 1.x: supported; lean-agents will not upgrade it". `tests/opencode-guard.test.mjs` fails if any install, `--update`, `--migrate` or `lean-update` plan contains a command that installs or upgrades OpenCode. Moving from 1.x to 2.x is your own step.

Why back up first: the session history lives in a database, `opencode.db`, and OpenCode 2 reportedly does not carry your old sessions over (owner report, 2026-11-06; **VERIFY** against the OpenCode 2 release notes). Copy it (never move it) before any major upgrade.

### Upgrade apply and `--undo` (#80 part 2, P6, 2026-11-18)

`scripts/lib/opencode-upgrade.mjs`, `scripts/lib/backup-stamp.mjs`, `--upgrade-agent opencode --yes` / `--undo`. Proof: `tests/opencode-upgrade.test.mjs` (fake binaries, fake installer, temp HOME) and CI job `real-upgrade-opencode` (`tests/real-upgrade-opencode.sh` / `.ps1`).

- **Gate:** `--backup --yes` writes `STAMP.json` into the finished backup folder after the sha256, count and frozen-copy checks. Apply needs that stamp, re-hashes the backup against `MANIFEST.sha256`, and needs the live data to equal the backup (first apply) or the frozen copy (after an earlier `--undo`, which leaves the 1.x sessions made through `opencode1`). Anything else refuses with nothing written.
- **Steps** (`state.json` `upgrade`, saved before and after each): `backup`, `opencode1`, `install2x`, `config`, `dcp`. Rollback and `--undo` use each step's own undo in reverse. `config` and `dcp` write through `upgradeApply` with separate fsops backup folders, so the original config bytes come back.
- **2.x install:** Linux and macOS use the pinned installer through `--install-agent`'s code (`fromUpgrade`: the 1.x binary being at `~/.opencode/bin` is expected, it was copied out and sha256-checked by `opencode1`). Install, version, PATH order and removal are checked by CI real-windows (2026-11-19). A 2.x that was already installed is kept and not removed by undo.
- **Data:** apply only reads it. `--undo` and a rollback after the live data changed stage a sha256-checked copy of the frozen copy next to the live folder, move the live db, `-wal`, `-shm`, `storage` and `snapshot` to `backups/opencode2-db-<ts>/` and rename the staged items into place; the live folder's other files (auth, logs) stay. If the frozen copy has fewer sessions than the backup, the backup is the source. A failed rename puts the old items back.
- **Processes:** apply and `--undo` refuse while an `opencode` process runs (image name; the 2.x background service is one). Apply starts none, so there is no service of ours to stop. **VERIFY:** whether a 2.x started by the user leaves a service that outlives its command on every OS (the CI test stops it itself).
- **State file:** apply on a machine without a lean-agents install writes a minimal `state.json` for the journal; after `--undo` it stays with the journal `undone` and nothing else (harmless). The journal is saved through a temp file and rename.
- **Frozen copy trust:** at apply start the frozen copy must equal the backup's manifest or count at least the backup's sessions (`opencode1 run` changes only the frozen db, no state files are needed); a restore copies the frozen copy back unless it counts fewer sessions than the backup, then the backup is the source.

- **VERIFY:** that the upstream 2.x installer never runs `opencode` against the live data folder (apply relies on it; CI asserts the live data hash is unchanged after apply).

## Fresh-machine workflow (#179 PR6, 2026-11-18)

`.github/workflows/fresh-machine.yml` runs nightly (05:23 UTC) and on `workflow_dispatch` only, never on a pull request. It packs the release files once, then runs the real `install.sh` / `install.ps1 --everything --yes` and `--doctor` (must exit 0) from `LEAN_AGENTS_DIST`, into a throwaway HOME, on `macos-latest`, `windows-latest` and an `ubuntu:24.04` container. A failure opens or comments one `version-watch` issue, "Fresh-machine install breaks". `force-fail` tests the report.

| Leg | What is hidden | How |
| --- | --- | --- |
| macOS | brew, Node.js, npm, git, gh, nvm | `/opt/homebrew` and `/usr/local/Homebrew` are renamed (throwaway VM); PATH is `/usr/bin:/bin:/usr/sbin:/sbin`, `env -i` |
| Windows | Node.js, npm, git, gh, nvm | PATH entries matching them are dropped; `USERPROFILE` is a temp folder |
| Linux | everything | the stock image has none; only `curl` and CA certificates are added for `install.sh` |

**Limit:** this is a PATH trick on a runner image, not a bare machine. `/usr/bin/git` (the Xcode shim) stays on macOS, winget and the Windows system tools stay, and a per-user install on the runner could still be found by absolute path. Corporate proxy and TLS inspection are only provable on the owner's PC.

**VERIFY** (first nightly runs decide): Homebrew's pinned installer unattended on macOS runners (including the Xcode CLT step); nvm-windows without admin on `windows-latest`; `--everything` as root in the Ubuntu container; `actions/download-artifact` inside the container. Not run locally: no real binaries on the owner's machine.

## Agent CLI upgrades within a major (#182 PR3, 2026-11-18)

`--update` runs, after the one confirm, one command per plan row with action `update` for an agent lean-agents installed (`agents.json`): Claude Code `claude-installer.sh <pin>`, OpenCode 2 `opencode-installer.sh --version <pin> --no-modify-path`, Copilot CLI `npm install -g [--prefix] @github/copilot@<pin>`. The installer scripts are the same sha256-pinned ones as `--install-agent`. `state.json` keeps `from` and `reinstall` (the same command at the previous version) next to each command; `--uninstall` does not run it. Never moved: OpenCode 1.x, another major, an agent you installed, the VS Code Copilot extension, Cursor (its installer takes no version) and Antigravity (no pin). Proof: `tests/agent-upgrade.test.mjs` (synthetic rows, temp HOME, no binaries).

`--update --undo` (#278, 2026-11-18, engine tests with stubs only) reinstalls, per agent, the oldest saved `from` with the same installer argv at that version (a pre-release tag is kept as printed by `--version`); the downloaded installer script is removed by a final step even when an earlier step failed. `--uninstall` does not undo agent upgrades.

**VERIFY** (no real binary yet; the nightly proof is PR6): that the Claude and OpenCode installers accept a version older than the installed one (downgrade, needed by the undo) and a newer one over an existing install; that the Windows installers (not offered yet) behave the same; `npm install -g` over an older Copilot CLI behind a proxy.
